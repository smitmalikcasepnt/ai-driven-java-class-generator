How our framework's AI agent drives a real web application through Playwright (MCP), harvests every locator it touches, and writes a clean, well-structured Selenium + TestNG Java class — so from the second run on, the test executes as plain Java with no AI and no Playwright in the loop.

💡

The core idea. A manual test case usually gets automated by a person, by hand — slow, and different every time. Here, the AI agent runs the test case one time in a real browser, watches exactly which elements it clicks and types into, captures a stable locator for each, and turns that recording into a proper Java test class. The messy, one-time discovery work is done by AI; the durable output is ordinary, reviewable code the team already knows how to run.

✦ What the framework actually does

Four connected capabilities turn a single guided browser run into production-quality, structured Java that fits the team's existing test project.

🌐 Capability 1

Browser Automation via Playwright (MCP)

The AI drives the real application exactly as a tester would — the one-time discovery run.

  • Reads the test case, logs in, connects to the right app, workspace & environment
  • Performs each step in a live browser and captures the actual path taken
  • Records enabling clicks the prose skips — expanding menus, tabs & collapsed panels
✔ A faithful, executable recording of the real user journey.
🎯 Capability 2

Locator Harvesting & Verification

For every element it touches, it derives the most stable locator — and proves it before writing code.

  • Picks a locator by a strict priority ladder (id → name → data-* → text → scoped CSS)
  • Rejects fragile locators — dynamic IDs, GUIDs, index-based paths
  • Re-resolves each locator in the live DOM to confirm it hits exactly one visible element
✔ Locators that survive replay — no fix-and-rerun churn later.
☕ Capability 3

Well-Structured Java Emit

The output isn't a script dump — it's a clean class that matches the repo's conventions.

  • One named By constant per element, named by its role
  • One private helper per test step, with real TestNG assertions on every check
  • Login handled by a shared Base; app connect by a reusable ConnectHelper
✔ Readable, reviewable code — filed into the right module package.
📊 Capability 4

Compile, Run & Report

The class is dropped into the live Maven project, compiled, and wired for reporting.

  • Emits a scoped TestNG suite and an artifact copy alongside the recording
  • Compile-checked on generation so it's ready to run, not just written
  • A report listener routes results to a timestamped, per-module HTML report
✔ Runnable from an IDE or CI the moment it's generated.

→ How a class gets generated

Every generation follows the same six-step pipeline — the first three happen in the browser, the last three produce and validate the code.

1

Fetch

Pull the test case & its steps from Azure DevOps / TFS.

2

Connect

Classify the app, log in, and connect the org / workspace / app.

3

Drive & Harvest

Run each step in the browser; record a locator per interaction.

4

Verify

Re-resolve every locator in the live DOM — exactly one visible hit.

5

Emit

Write the Java class, TestNG suite & artifact copy.

6

Compile

Build it in the Maven project & confirm the class file exists.

≡ How it chooses a locator

The single biggest cause of flaky automation is a bad locator. The AI walks this priority ladder for every element and always prefers the most stable option available.

#PrefersExampleWhen it's used
1Static IDBy.id("astSkInboxTemplateTitle")The ID is stable — no GUID, number, or copy suffix
2NameBy.name("ddlFieldCategory0_input")Element carries a stable name attribute
3Stable attribute[data-code='ACT_APPROVE']A unique data-* or role attribute exists
4Visible text//*[normalize-space()='Skills']Menu items, labels & buttons identified by text
5Scoped CSS#astSkInboxActions button[data-code]A child within a stable parent container
6Class combolabel.k-checkbox-label[for='…']Last resort when nothing above is available
🛡️

Verify before emit. Playwright's browser is forgiving; Selenium is not. So before any locator is written into code, the agent re-resolves it against the same live page the way Selenium will — and only keeps it if it matches exactly one visible element. Each mismatch caught here saves a full fresh-login rerun later.

{ } Anatomy of a generated class

The emitted code is deliberately conventional — no page-object indirection, one class per feature, and clear traceability back to the source test case.

// Filed by feature into the right module package — not by test-case id package CasePointARA_Module.ASTRA.Inbox; // Login + driver come from Base; app-connect from ConnectHelper — never re-derived public class InboxTemplate extends Base { // One named locator per element, chosen by the stability ladder private static final By INBOX_TITLE = By.id("astSkInboxTemplateTitle"); private static final By SAVE_SKILL_BTN = By.cssSelector("[data-code='ACT_SAVE']"); @Test(description = "Verify Inbox Template section — TC1586576") public void verifyInboxTemplateSection() { ConnectHelper.connectAstra(driver, wait, WORKSPACE_NAME); // shared connect step1_openInboxTemplate(wait); step2_enterTitleAndSave(wait); // each step = one private helper } // … one step<N>_ helper per test step, each with a real TestNG assertion … }

Alongside the class, generation also produces a scoped TestNG suite XML, an artifact copy of the class kept with the recording, and a report listener wired in — so it's runnable from an IDE or CI immediately, with results routed to a timestamped, per-module HTML report.
